# 기준선 업데이트 운영 안내

## 1. 어떤 업데이트인가요?

| 목적 | 권장 경로 | 현재 적용 기준 변경 |
|---|---|---|
| 기존 분야의 논문 선택·최소 길이 변경 | 관리자 페이지 재계산 → 검토 → 적용 | 적용 시 변경 |
| 같은 분야의 새 논문 추가 | 루트 분야 폴더에 MD 추가 → 배포/파일 반영 → 관리자 재계산 | 적용 시 변경 |
| 초기 포함 기준 파일 갱신 | 로컬 CLI 전체 재생성 → 검토 → 저장소 커밋 | 기존 레지스트리에는 자동 적용 안 됨 |
| 새 PDF 묶음으로 비교 | PDF Stage 1 모드 | 독립 기준 생성, 네 분야 포인터 자동 변경 안 됨 |
| GNU 평균·/10k 및 토픽 기준 생성 | 기존 PDF 모드 → 판정 검토 → 기준 생성 | 독립 GNU 기준 생성 |
| 새 분야 코드·분석 규칙 추가 | 코드 변경·검증 및 재계산 | 설정·호환성 변경 필요 |

기준은 입력 논문, 전처리, 판정 규칙, 모델, 분모, 통계가 함께 결정합니다. 이름만 바꾸거나 CSV 숫자만 편집해서는 재현 가능한 업데이트가 되지 않습니다.

## 2. 업데이트 전 준비

1. 로컬 또는 영구 저장소 환경인지 확인합니다. Render 무료 서비스에서 만든 버전·이력은 다음 배포·재시작 시 소실됩니다.
2. 보관할 기존 `data/` 전체를 일관된 상태로 백업합니다. 관리자 ZIP은 해당 작업 자료이며 레지스트리 전체 백업은 아닙니다.
3. 업데이트 목적을 정합니다. 예: JOC 표본에서 잘못 변환된 논문 제외, 새 연도 논문 추가, 최소 본문 길이 상향.
4. 같은 분야·문서 유형·시기인지 확인합니다. 연구논문과 리뷰·SI 혼합은 표현 분포를 바꿀 수 있습니다.
5. Python·spaCy·모델과 규칙 버전을 확인합니다. 현재 환경은 Python 3.12 권장, spaCy 3.8.11, en_core_web_sm 3.8.0입니다.
6. 작업자 이름과 변경 사유를 준비합니다. 이름은 인증 계정이 아니라 이력 표기입니다.

## 3. 관리자 페이지로 업데이트

### 3.1 접속과 로그인

로컬은 `http://127.0.0.1:8001/admin`, 배포는 `https://gnu-10team.onrender.com/admin`입니다. 첫 실행 시 서버의 `data/admin/initial_password.txt`에 생성된 비밀번호를 사용합니다. 로컬에서는 다음 명령으로 확인합니다.

```sh
cat data/admin/initial_password.txt
```

배포 서버의 파일은 로컬 PC 파일과 별개입니다. 서버 파일에 접근할 수 있는 운영 경로가 필요하며 무료 플랜에서 Render Shell/SSH 사용 가능 여부를 확인해야 합니다. 현재 앱에는 최초 비밀번호를 웹에서 발급·조회하거나 재설정하는 화면이 없습니다. 비밀번호를 Git에 추가하거나 공개 로그에 출력하지 않습니다.

### 3.2 현재 기준 확인

1. 왼쪽에서 분야(CM·IC·JOC·JPC_C)를 선택합니다.
2. 현재 기준 이름·버전 ID·포함/제외 논문 수·섹션별 지표·적용 시점을 기록합니다.
3. 버전 보관함과 변경 이력을 확인하여 마지막 업데이트를 파악합니다.
4. 비교할 새 논문 목록이나 수정 목적이 현재 버전과 어떻게 다른지 정리합니다.

### 3.3 자료 선택과 재계산

1. **새 버전 재계산** 또는 재계산 탭을 엽니다.
2. 새 기준 이름을 입력합니다. 예: `유기화학 · JOC · 2026-11 표본 보완`.
3. 본문 최소 단어 수를 지정합니다. 기본 1,000, 허용 범위 1,000~20,000입니다. 임계값 상향은 짧은 논문을 더 제외합니다.
4. 변경 사유를 구체적으로 입력합니다. 예: `읽기 순서가 잘못된 2편 제외, 신규 3편 추가`.
5. 사용할 마크다운을 선택합니다. API는 2~100개, 서로 다른 파일 최소 2개를 요구합니다. 중복 파일명은 제거합니다.
6. **선택 자료로 재계산**을 실행합니다. 현재 기준은 계속 유지됩니다.
7. 대기 → 실행 중 → 완료/실패 상태를 확인합니다. 관리자 화면은 진행 중 상태를 주기적으로 조회합니다.

문서 목록은 해당 서버 프로젝트 루트의 `<분야>/*.md`입니다. 관리자 화면에는 마크다운 업로드·편집 기능이 없습니다. 다른 분야 폴더를 자동 검색하거나 하위 폴더를 재귀 검색하지 않습니다. 대소문자 확장자와 파일명도 확인합니다.

### 3.4 재계산 내부 동작

1. 선택 파일의 바이트·SHA-256을 `data/admin/jobs/<작업ID>/markdown/`에 복사합니다.
2. `hedge_baseline.py`, `engine_local.py`, `rvtool.py`, `extract_pdf.py`, 마크다운 어댑터, 관리자 워커를 `rules/`에 복사하고 해시를 저장합니다.
3. 작업자·사유·분야·현재 기준 ID·선택 목록·최소 길이·새 기준 ID를 `job.json`에 기록합니다.
4. 별도 프로세스가 고정 사본으로 실행됩니다. 기존 `.venv-baseline/bin/python`이 있으면 우선 사용하고, 없으면 서버 Python을 사용합니다.
5. 마크다운 구조 검사 후 통과 논문만 표준 TXT·TSV로 작성합니다. 통과가 2편 미만이면 실패합니다.
6. Stage 1 집계 CLI를 실행합니다. 처리 검사에 Fail이 있으면 등록하지 않습니다.
7. `per_paper.csv`로 각 기준 지표의 n·중간값·최소·최대를 독립 재계산해 `baseline.csv`와 대조합니다.
8. 새 기준 JSON을 원자적으로 저장하고 읽기 해시를 검사합니다. 입력 지문·규칙 해시·환경·부모 버전·설정을 보존합니다.
9. 서버가 결과 해시를 확인하고 버전 보관함에 **검토 대기** 상태로 등록합니다.

관리자 재계산은 동시에 하나만 허용합니다. PDF 백그라운드 작업과 실행 워커를 공유하므로 PDF 처리 중이면 대기가 길어질 수 있습니다. 워커의 외부 실행 제한은 1,800초이며 서버가 종료되면 중단 작업은 다음 시작에서 실패 처리됩니다. 자동 이어하기 기능은 없습니다.

### 3.5 결과 검토

**결과 검토/미리보기**에서 다음을 확인합니다.

- 현재 기준 대비 포함 편수 변화와 새로 포함·제외된 문서.
- `markdown_gate`의 문서별 Pass/Fail과 제외 사유.
- 모든 섹션의 n·중간값·범위, 특히 RD와 RES·DIS의 구성 변화.
- 최소 길이 변경으로 특정 유형의 논문만 남지 않았는지.
- 결과 ZIP의 `run.log`, `analysis/markdown_gate.json`, `analysis/2_baseline/checks.json`.
- `per_paper.csv`의 극단값, `common_verbs.csv`의 전문어·품사 오인.
- `evidence.csv`의 표현별 문맥, 잘린 문장, 표·캡션·러닝 헤더 혼입.
- 새 표본에서 헷지·강조 표현별 20~30건 등 충분한 근거 표본을 읽고 자동 판정 오차 확인.

구조 검사 통과만으로 연구자 검토가 완료된 것은 아닙니다. 생성 JSON은 `needs_review=true`이며 현재 관리자 UI에는 이를 최종 승인 완료로 전환하는 별도 기능이 없습니다.

### 3.6 적용

1. 검토할 버전의 **이 버전 적용**을 누릅니다.
2. 적용 사유를 입력하고 실행합니다.
3. 현재 기준의 버전 ID·편수·지표가 바뀌었는지 확인합니다.
4. 변경 이력의 작업자·시각·사유·이전/새 버전이 맞는지 확인합니다.
5. 진단 화면을 새로고침하고 같은 분야로 원고를 다시 분석합니다.

적용 요청은 화면이 알고 있던 `expected_current_id`와 실제 현재 기준이 같아야 합니다. 다른 작업자가 먼저 변경했다면 409로 거절하므로 새로고침 후 다시 검토합니다. 보관 JSON 해시·엔진 버전·핵심 규칙 해시가 맞지 않아도 적용을 막습니다.

기존 분석 결과는 자동 재분석하지 않습니다. 과거 결과의 `baseline_id`는 그때 사용한 버전을 가리킵니다. 이전 기준을 선택한 오래된 화면에서 새 분석을 요청하면 409로 새로고침을 안내합니다.

### 3.7 복원

버전 보관함에서 과거 적용 버전의 **이 버전으로 복원**을 누르고 복원 사유를 입력합니다. 과거 버전 파일을 다시 계산하는 대신 현재 적용 포인터를 그 버전으로 바꾸고 `restored` 이력을 추가합니다. 이전 이력을 지우지 않습니다.

이전에 적용한 적 없는 초안은 복원 대상이 아니라 새 적용 대상입니다. 핵심 규칙이 바뀐 뒤에는 과거 규칙의 기준 복원이 거절될 수 있습니다. 분석기 호환성을 맞추거나 현재 규칙으로 재계산해야 합니다.

## 4. 새 마크다운 추가·수정

1. 적법하게 확보한 연구논문을 마크다운으로 변환합니다. 현재 저장소의 문서는 Kordoc 변환본이며 이 웹앱에 Kordoc 변환 API가 포함된 것은 아닙니다.
2. 분야에 맞는 프로젝트 루트 `CM/`, `IC/`, `JOC/`, `JPC_C/`에 `.md` 파일을 넣습니다. 파일 stem이 문서 ID이므로 중복되지 않게 정합니다.
3. 서론·방법·결과논의·결론·참고문헌 헤딩, 두 단 읽기 순서, 표·그림·첨자, 문장 잘림을 확인합니다.
4. 표로 변환된 본문은 어댑터가 제외할 수 있으므로 원문과 대조해 마크다운을 보완합니다. 누락된 문장을 추측해서 작성하지 않습니다.
5. 로컬 앱은 같은 폴더의 새 파일을 문서 조회 시 읽습니다. Render는 새 마크다운을 저장소에 커밋·푸시해 배포해야 반영됩니다.
6. 관리자 자료 목록을 다시 열어 선택하고 재계산 → 검토 → 적용합니다.

현재 지원 분야 코드는 네 개로 제한됩니다. 새 분야를 추가하려면 `backend/admin.py`의 GROUPS·입력 Literal, 빌드 스크립트 GROUPS·표시 이름, 프런트엔드 분야 탐색, 초기 기준 등록을 함께 검토해야 합니다. 폴더만 추가해도 자동 분야가 생기지는 않습니다.

## 5. 초기 포함 기준을 CLI로 다시 만들기

이 절은 저장소에 배포할 `baselines_markdown/` 기본 자료를 갱신하는 개발 작업입니다. 관리자 이력을 만드는 경로와 다릅니다. 기존 산출물을 보존할 별도 체크아웃이나 백업에서 수행합니다.

### 5.1 고정 환경

```sh
python3.12 -m venv .venv-baseline
.venv-baseline/bin/python -m pip install -r requirements.txt
.venv-baseline/bin/python -m pip install 'https://github.com/explosion/spacy-models/releases/download/en_core_web_sm-3.8.0/en_core_web_sm-3.8.0-py3-none-any.whl'
.venv-baseline/bin/python -c 'import spacy; print(spacy.__version__, spacy.load("en_core_web_sm").meta["version"])'
```

예상 버전은 `3.8.11 3.8.0`입니다. Python 패치 버전까지 정확히 재현하려면 현재 포함 자료의 기록(3.12.10)도 참고합니다.

### 5.2 기존 출력 정리와 표준 입력 생성

어댑터는 출력 폴더를 만들지만 과거 통과 문서 파일을 자동 삭제하지 않습니다. 이전에 통과했던 문서가 이번에 제외되면 오래된 TXT·TSV가 남아 집계에 들어갈 수 있습니다. **반드시 백업한 뒤 해당 생성 출력만 비우거나 새 작업 공간에서 생성**합니다. 원본 MD 폴더를 지우면 안 됩니다.

```sh
# baselines_markdown의 기존 출력은 별도 보관한 상태에서 실행
.venv-baseline/bin/python scripts/build_markdown_baselines.py
```

기본 CLI는 네 분야 전체를 처리하고 `baselines_markdown/<분야>/1_markdown_input/`, `markdown_gate.json`을 만듭니다. 기본 최소 전처리 길이는 1,000입니다. 사용자 지정 문서·출력·길이는 Python `prepare(group, source_dir, output_dir, documents, min_words)` 함수가 지원하지만 기본 명령행 옵션으로 노출되어 있지는 않습니다. 선택·임계값 변경은 관리자 경로가 편리합니다.

### 5.3 네 분야 집계

```sh
for group in CM IC JOC JPC_C; do
  .venv-baseline/bin/python section-verb-hedge-baseline/scripts/hedge_baseline.py "baselines_markdown/$group/1_markdown_input" "baselines_markdown/$group/2_baseline" --max-papers 25 || break
done
```

`--max-papers`는 통과 후 입력 논문 수를 수용하는 상한입니다. 원본 파일을 25개로 강제로 자르거나 Fail 문서를 포함시키는 옵션이 아닙니다. 현재 25편 체계에서 사용하며 더 늘리면 실제 입력 수에 맞춰 상한을 검토합니다.

### 5.4 처리 검사 및 JSON 생성

```sh
.venv-baseline/bin/python - <<'PYCODE'
import json
from pathlib import Path
for group in ('CM','IC','JOC','JPC_C'):
    p=Path('baselines_markdown')/group/'2_baseline/checks.json'
    failed=[x for x in json.loads(p.read_text())['items'] if x['result']=='Fail']
    print(group, 'PASS' if not failed else failed)
    assert not failed
PYCODE
.venv-baseline/bin/python scripts/finalize_markdown_baselines.py
```

마무리 스크립트는 분야별 `baseline.json`, `section_audit.md`, 전체 README·summary·hashes를 만들고 로컬 `data/baselines/`에도 복사합니다. 출처 산출물 SHA-256과 포함 편수를 확인합니다.

**현재 마무리 스크립트에는 입력 25편, Python 3.12.10 등의 설명값이 고정되어 있습니다.** 실제 입력 수·환경을 바꿨다면 생성 전에 이 메타데이터와 보고서 템플릿도 맞춰야 합니다. 그대로 실행한 결과를 실제 환경과 일치한다고 가정하지 않습니다.

기본 번들 ID는 분야와 입력 MD 해시의 조합으로 생성됩니다. 입력은 같고 규칙·모델만 바꾼 경우 ID가 바뀌지 않을 수 있습니다. 이때 같은 ID의 내용 덮어쓰기를 운영 버전 관리로 사용하지 말고, 관리자 재계산의 새 UUID 버전 또는 명시적인 ID 정책 변경을 사용합니다.

### 5.5 검토·배포·적용의 차이

1. 생성 CSV·JSON·제외 사유·근거를 검토합니다.
2. 테스트와 `git diff --check`를 수행합니다.
3. 의도한 마크다운·생성 기준·문서를 커밋합니다. `data/`, ZIP, PDF, 자격 정보는 제외합니다.
4. 배포 후 새로 초기화한 서버는 새 번들을 초기 기준으로 등록합니다.
5. **이미 `data/admin/registry.json`이 있는 서버는 새 번들을 현재 기준으로 자동 적용하지 않습니다.** 운영 업데이트는 관리자 재계산·적용으로 진행합니다. 번들 파일 변경만으로 이력 있는 현재 기준을 교체하지 않습니다.

운영 레지스트리나 버전 JSON을 직접 편집하면 해시·현재 포인터·이력이 어긋날 수 있으므로 적용 API를 사용합니다.

## 6. PDF에서 새 기준 만들기

Stage 1 PDF 모드에서 2~10개의 서로 다른 PDF를 선택하고 이름을 입력합니다. 추출·품질 검사·집계·검증 그림을 생성합니다. 통과 논문이 2편 미만이면 등록하지 않습니다. 실패 원인을 수정한 뒤 새 작업으로 실행합니다. 새 독립 기준은 PDF 작업에서 선택할 수 있지만 관리자 네 분야 포인터에 자동 연결되지 않습니다.

기존 GNU 모드에서는 완료 작업의 후보·선행연구 판정을 먼저 검토한 뒤 기준 생성 작업을 합니다. 판정 수정은 이미 만든 기준을 자동 갱신하지 않으므로 새 기준을 다시 생성해야 합니다. 두 모드의 지표·집계는 [분석 방법](analysis-and-upstream.md)을 따릅니다.

## 7. 분석 규칙·모델 변경

- 헷지 어휘나 제외 규칙, 문장 분리, NONPROSE, 품사 모델을 바꾸면 기준과 원고를 같은 환경으로 재분석해야 합니다.
- 관리자 새 버전은 핵심 규칙 해시를 저장합니다. 원고 비교와 적용에서 현재 코드와 맞지 않으면 중단합니다.
- 초기 포함 번들은 관리자 생성 버전과 달리 `rule_hashes`가 없을 수 있습니다. 모든 과거 번들에 완전한 코드 무결성 검사가 있다고 해석하지 않습니다.
- 엔진 버전·모델 상수를 바꿀 때 서버 버전 검사, 빌드 스크립트, 요구 패키지, 테스트·문서를 함께 갱신합니다.
- 엔진을 바꾼 결과와 과거 결과를 비교할 때 입력 변화와 규칙 변화를 분리해서 보고합니다.

## 8. 실패 대응

| 증상 | 확인 및 조치 |
|---|---|
| 401 관리자 로그인 필요 | 세션 만료·서버 자격 정보 초기화 확인, 다시 로그인 |
| 403 다른 출처 | 프록시·도메인·Origin과 요청 base URL 일치 확인 |
| 409 진행 중 작업 | 기존 재계산 완료/실패까지 기다림 |
| 409 현재 기준 변경 | 새로고침 후 현재 버전 확인 |
| 해시 불일치 | 보관 파일 수동 변경·불완전 복원 확인, 원본 백업 복원 또는 새 재계산 |
| 통과 2편 미만 | `markdown_gate.json`의 헤딩·순서·길이 사유 확인 |
| 분석 단어 수 부족 | 공백 단어 수와 알파벳 토큰 분모 차이 확인 |
| 모델 버전 오류 | 서버와 `.venv-baseline` 양쪽 설치 환경 확인 |
| 재시작 후 버전 소실 | 임시 파일시스템 여부 확인, 영구 저장·백업 구성 |
| 새 MD가 목록에 없음 | 올바른 서버의 루트 분야 폴더, `.md`, 배포 반영 확인 |

실패 작업도 오류와 이력을 남기고 현재 기준은 바꾸지 않습니다. 작업 ZIP과 `run.log`를 확인하되 민감한 논문·원고 내용이 포함될 수 있으므로 공개 공유 전에 검토합니다.
