# 개발자 제안: Render 무료 티어 운영과 개선 방향

작성일: 2026-10-31. 현재 배포 설정·코드·공식 플랜 사양 및 단일 요청 측정에 기반한 제안입니다. 아래 개선 항목과 유료 전환은 아직 적용하지 않았습니다. 요금·정책·운영 상태는 변경될 수 있습니다.

## 1. 판단

**현재 Free 플랜으로 문서 열람과 간헐적인 짧은 원고 진단은 가능합니다. 관리자 기준 변경·이력 보관·PDF 일괄 처리까지 포함한 지속 운영에는 현재 구성이 적합하지 않습니다.**

현재 프로젝트는 무거운 외부 AI API가 아니라 서버 안의 spaCy 모델과 규칙 엔진을 실행합니다. 따라서 API 호출 요금보다 서버 CPU·메모리·프로세스 수, 실행 데이터 보존이 주요 운영 조건입니다.

## 2. 확인한 현재 구성

| 항목 | 확인 결과 |
|---|---|
| 서비스 | `gnu_10team`, https://gnu-10team.onrender.com |
| 실행 플랜 | `serviceDetails.plan=free` |
| Free 사양 | 0.1 CPU · RAM 512MB |
| 앱 서버 | Python 3.12, FastAPI, Uvicorn `--workers 1` |
| 분석 모델 | spaCy 3.8.11 · en_core_web_sm 3.8.0 |
| 백그라운드 처리 | PDF·관리자 재계산이 프로세스 워커 1개 공유 |
| 저장 | 프로젝트 루트 `data/`, JSON·PDF·엑셀·CSV·작업 로그 |
| 영구 디스크 | 현재 미연결, Free에서는 연결 불가 |
| 같은 워크스페이스 | `gnu-protein`도 Free로 등록되어 있음 |

서비스 API의 `buildPlan=starter`는 빌드 관련 값이며 실행 플랜이 유료 Starter라는 뜻이 아닙니다. 실행 사양은 `serviceDetails.plan`으로 확인했습니다. [Render 컴퓨트 사양](https://render.com/docs/compute-plans)

## 3. 실제 측정 결과와 한계

배포 서버에 순차적으로 요청했으며 부하 테스트는 수행하지 않았습니다.

| 요청 | 응답 | 경과 시간 |
|---|---|---:|
| `/api/health` | HTTP 200 | 약 0.28초 |
| `/api/baselines` | HTTP 200 | 약 0.30초 |
| `ex.txt` 서론을 JOC 기준으로 `/api/manuscript` 분석 | HTTP 200, Stage 1 결과 포함 | 약 32.45초 |

시간에는 클라이언트와 서버 사이의 통신 및 서버 처리가 포함됩니다. 서버 기동 직후인지, 모델 캐시가 준비됐는지에 따라 달라질 수 있습니다. 짧은 예시 하나의 성공으로 긴 원고·PDF·동시 사용자 처리를 보장하지 않습니다. 초당 처리량이나 허용 동시 사용자 수는 아직 산정하지 않았습니다.

별도로 로컬 macOS에서 같은 예시를 임시 저장소로 분석한 단일 실행은 약 1.56초, 부모·자식 프로세스 RSS 합계의 표본 최대 약 251.7MiB였습니다. 약 0.15초 간격의 프로세스 샘플이므로 짧은 피크를 놓칠 수 있고 공유 메모리 중복도 포함될 수 있습니다. Render Linux 인스턴스의 실제 메모리 측정값이 아니며 512MB 환경의 안전성을 증명하지 않습니다.

Render 실제 최대 메모리·CPU 사용률·월 실행 시간·빌드 분·대역폭 잔여량은 이번 확인에서 수집하지 않았습니다. 메모리 부족 장애를 재현하거나 확인한 것도 아닙니다. 아래 메모리 우려는 코드 구조와 자원 한도에 따른 평가입니다.

## 4. 기능별 적합성

| 기능 | Free 판단 | 근거 |
|---|---|---|
| 앱·문서 열람 | 가능 | 큰 분석 연산 없이 제공 |
| 포함 기준 조회 | 가능 | 작은 추적 JSON 자료 사용 |
| 짧은 원고의 간헐적 분석 | 가능, 지연 수용 필요 | 예시 1회 정상 완료, 약 32초 |
| 긴 원고·동시 요청 | 추가 검증 필요 | 모델 연산·별도 프로세스의 자원 경쟁 |
| PDF 여러 편 분석 | 상시 제공에는 비권장 | PDF 추출·품질 검사·레이아웃 이미지·엑셀 생성 |
| 관리자 마크다운 재계산 | 로컬 수행 권장 | 입력 전체 처리·여러 프로세스·검산 필요 |
| 적용 기준·이력 보관 | 현재 구성으로 불가 | `data/`가 임시 파일시스템 |
| 관리자 자격 정보의 안정적 유지 | 현재 구성으로 불가 | 실행 데이터 초기화 시 비밀번호·서명 키 재생성 |

기본 마크다운 100편의 총 크기는 약 5MiB, `baselines_markdown/`은 약 6MiB, 프런트엔드는 약 1MiB입니다. 이는 파일 크기이며 실행 메모리가 아닙니다. 기본 자료 크기보다 분석 처리 과정이 더 중요한 자원 부담입니다.

## 5. Free와 충돌하는 현재 구조

### 5.1 유휴 중지에도 실행 데이터 소실

Free 서비스는 15분간 인바운드 트래픽이 없으면 중지되며 다음 접속의 기동에 약 1분이 걸릴 수 있습니다. 재배포·재시작뿐 아니라 유휴 중지에서도 실행 중 생성한 로컬 파일이 사라집니다. Free는 영구 디스크·Shell·SSH를 지원하지 않습니다. [공식 Free 제한](https://render.com/docs/free)

이 프로젝트에서 소실 대상은 분석 결과, 업로드 PDF, 새 기준, 현재 적용 포인터, 변경 이력, 관리자 자격 정보입니다. GitHub의 논문 마크다운·초기 기준·문서는 새 배포에서 다시 제공됩니다. 저장 형식을 JSON에서 SQLite로만 바꿔도 임시 저장소 문제는 해결되지 않습니다.

### 5.2 관리자 비밀번호 조회 경로

현재 최초 비밀번호는 서버 `data/admin/initial_password.txt`에 생성됩니다. 무료 서버에는 Shell·SSH가 없으므로 파일을 읽는 기존 안내는 Free 운영 절차로 충분하지 않습니다. 현재 앱에 웹 비밀번호 조회·재설정 기능은 없습니다.

자격 정보 초기화가 반복되지 않도록 영구 저장을 도입하거나, 별도의 인증 설정 방식을 구현해야 합니다. 관리자 비밀번호를 공개 로그·문서·GitHub에 넣는 방식은 사용하지 않습니다. 이 제안에서 인증 코드를 변경한 것은 아닙니다.

### 5.3 모델·프로세스와 동시 요청

- `backend.analysis.language()`는 서버 프로세스에 spaCy 모델을 캐시합니다.
- 원고 Stage 1은 별도 Python CLI를 실행해 해당 프로세스에서도 모델을 사용합니다.
- 관리자 재계산은 워커·외부 Python·집계 CLI의 여러 실행 단계를 거칩니다.
- PDF 작업은 추출·분석뿐 아니라 이미지·엑셀 산출물을 생성합니다.
- Uvicorn 워커 1개는 원고 요청 전체를 한 번에 하나만 처리하도록 제한하는 설정이 아닙니다.

따라서 PDF 백그라운드 워커가 하나여도 원고 요청이 동시에 들어오면 모델·프로세스가 자원을 나눠 사용합니다. CPU가 작은 무료 서버에서 지연이 늘거나 메모리 여유가 줄 수 있습니다. 현재 이 우려를 검증할 동시 요청 시험은 수행하지 않았습니다.

### 5.4 누적 파일과 사용량

파일당 50MB 업로드를 허용하고 기존 PDF 모드는 최대 20개를 받습니다. 상한만 계산하면 한 작업에 약 1,000MB의 입력이 들어올 수 있으며, 이는 실제 사용량 측정이나 총 저장소 한도라는 뜻은 아닙니다. 추출본·이미지·내보내기까지 추가되며 현재 작업 보존 기간·일괄 정리 기능은 없습니다.

Free 실행 시간은 워크스페이스당 월 750시간을 공유합니다. 두 Free 서비스의 실제 가동 시간 합계에 주의해야 합니다. 빌드·대역폭에도 별도 월 포함량이 적용되며 현재 워크스페이스의 잔여량은 확인하지 않았습니다. [Free 사용량 정책](https://render.com/docs/free)

## 6. 제안 A: 무료 시연 구성 유지

목적이 발표·수업·비정기적 진단이라면 다음 구성으로 범위를 줄이는 것을 권합니다. **아래 항목은 제안이며 현재 구현 상태가 아닙니다.**

1. 기준 재계산과 PDF 일괄 처리는 로컬에서 수행합니다.
2. 검토한 기준을 저장소의 포함 자료로 배포하고 서버는 해당 기준으로 원고를 진단합니다.
3. 원고 분석에 별도의 동시 실행 제한과 대기·혼잡 안내를 둡니다. Uvicorn 워커 수와 별개의 제한입니다.
4. 현재 200,000자 허용 상한을 그대로 무료 서버의 실용 처리 용량으로 보지 않고, 대표 원고를 측정해 더 작은 운영 상한을 정합니다.
5. 공개 서버의 무거운 PDF·관리자 재계산 기능은 제한하거나 로컬 전용으로 분리합니다. 화면에서만 숨기지 않고 API에서도 통제합니다.
6. 결과 보관이 필요한 경우 사용자가 내려받을 수 있는 원고 결과 내보내기를 추가합니다. 현재 전체 원고 결과 내보내기가 모두 제공되는 것은 아닙니다.
7. 서버가 임시 결과만 보관한다는 점과 유휴 기동 대기를 사용자 흐름에 표시합니다.

무료를 유지하면서 관리자 상태까지 영구 보관하려면 외부 저장소 연동 등 별도 설계가 필요합니다. 이는 현재의 프로젝트 루트 JSON 저장 방식과 운영 구성을 변경하는 작업입니다. 단순 무료 DB 추가만으로 PDF·ZIP 등 모든 파일과 인증 상태가 함께 보존되는 것은 아닙니다.

## 7. 제안 B: JSON을 유지하는 소규모 실제 운영

프로젝트 루트 `data/` JSON 방식을 유지하려면 유료 웹 서비스와 해당 경로의 영구 디스크가 가장 직접적인 전환입니다.

| 후보 | CPU·메모리 | 공개 월 컴퓨트 가격 | 개발자 판단 |
|---|---|---:|---|
| Free | 0.1 CPU·512MB | $0 | 간헐적 진단·시연 |
| `0.5c-512mb` (기존 Starter) | 0.5 CPU·512MB | $7 | CPU 개선·영구 디스크 연결 가능, 메모리는 그대로 |
| `1c-2g` (기존 Standard) | 1 CPU·2GB | $25 | PDF·재계산까지 제공할 때 우선 검증할 후보 |

가격은 2026-10-31 확인한 [공식 가격표](https://render.com/pricing) 기준입니다. 영구 디스크는 GB당 월 $0.25로 별도입니다. 워크스페이스 요금·세금·추가 사용량은 포함하지 않았으며 실제 청구액은 결제 설정과 사용량에 따라 달라집니다.

유료 전환만으로 데이터가 보존되지는 않습니다. 실제 `data/` 경로에 디스크를 연결하고 기존 데이터를 사전에 백업·복원해야 합니다. 단일 앱 프로세스 전제도 유지합니다. 자세한 절차는 [배포·데이터 보관](render-deployment.md)을 참고합니다.

**권고:** 기준 관리·PDF·이력 보관을 모두 유지하려면 1 CPU·2GB와 영구 디스크를 시작 후보로 검증합니다. 이 사양도 다중 사용자 운영을 보장하는 확정 용량은 아닙니다. $7 플랜은 CPU와 기능 제약을 줄이지만 메모리 문제까지 해결한다고 가정하지 않습니다.

## 8. 전환 전 검증과 완료 조건

1. 실제 서론·서론+결과논의·긴 원고의 짧음/중간/최대 사례로 처리 시간을 측정합니다.
2. 원고 1건과 여러 요청, 원고+PDF, 원고+관리자 재계산 조합에서 CPU·최대 메모리·실패율·대기 시간을 기록합니다.
3. 실제 PDF 묶음과 25편 MD 재계산을 실행해 종료 시간·산출물 크기·메모리 피크를 확인합니다.
4. 요청 제한·작업 대기·파일 크기·보존 기간을 측정 결과에 맞춰 결정합니다.
5. 영구 저장 환경에서 관리자 로그인 → 기준 재계산·적용 → 재시작·재배포 → 현재 기준·이력 보존을 검증합니다.
6. 별도 백업을 복원해 같은 기준 ID·이력·자격 정보가 돌아오는지 확인합니다.

측정과 변경은 운영 데이터에 영향을 줄 수 있으므로 검증용 환경·자료를 우선 사용합니다. 이 문서는 부하 테스트·요금 변경·영구 디스크 연결·인증 개편을 실행했다는 기록이 아닙니다.
